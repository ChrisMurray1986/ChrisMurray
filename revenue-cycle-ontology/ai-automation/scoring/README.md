# Feasibility Scoring Worksheet

Runnable implementation of the gating framework (`../07-feasibility-gating.md`) and gate
profiles (`../08-use-case-gate-profiles.md`). Assess your organization once; get a computed
GO / CONDITIONAL / DEFER / KILL disposition for all 99 use cases plus a ranked list of the
remediations that unlock the most portfolio value.

## Files

| File | Role |

| `assessment.template.yaml` | Blank worksheet (generated by `score.py --init`). Copy, fill in, keep under version control — it *is* the assessment record. |

| `value.py` | Value engine — estimates per-UC/portfolio value, joins the feasibility assessment to disposition-adjust and price locked gates. |
| `example-org-profile.yaml`, `example-value-report.md/.html` | Value-model example for the same fictional org. |

## How to run

```bash
# 1. Create your worksheet
python3 score.py --init my-org.yaml

# 2. Fill it in (see scoring guidance below)

# 3. Score
python3 score.py my-org.yaml -o report.md --csv report.csv

# Optional: interactive HTML report (self-contained single file — share it, open anywhere)
python3 score.py my-org.yaml --html report.html
```

The HTML view shows disposition stat tiles, dimension maturity meters, the remediation
leverage chart, and a use-case table filterable by disposition, domain, and free-text search.
It is fully self-contained (no network access needed) and respects light/dark system themes.

## Filling in the worksheet

**Dimensions** (0–4): overall maturity per gate dimension, using the level anchors in
`07-feasibility-gating.md`. Score what is *operational today*, not what is planned or piloted.
When torn between two levels, take the lower — the framework is weakest-link by design, and
optimistic self-assessment produces GO dispositions that fail in implementation.

**Facets** (0 / 1 / 2 / `blocked`): the 103 specific readiness facts that appear as decisive
gates. Score `0` = absent, `1` = partial or in progress, `2` = operational. Facets marked
*(blockable)* may instead be scored `blocked`, meaning a legal or contractual prohibition
(e.g., a criteria licensor forbids programmatic use, a payer's portal ToS bans bots) — this
KILLs dependent use cases rather than deferring them.

Assessment discipline:
- Each facet should be scored by the person who operates that area, not centrally guessed.
- A facet is `2` only if you could demo it this week. "The vendor says it supports it" is `1`.
- Connectivity facets are judged against the payers covering ≥80% of the relevant volume.
- Record evidence/notes inline as YAML comments — the worksheet doubles as the audit trail.
- Not sure what "ready" looks like on your stack? `../14-implementation-patterns.md` gives per-facet
  sufficiency floors (Epic / Oracle Health / multi-EHR) and flags where vendors routinely oversell;
  `../../vendor-crosswalks/` carries module-level depth markers (licensed / lit / configured-to-depth).
- **2026-07 floor note:** five facets were added and several floors deepened (file 14 §8).
  Assessments filled before that stamp score the new facets as absent and are not comparable
  on the revised floors — re-score before reconciling or re-running packets.

## How dispositions are computed

Per use case, from `gate-vectors.yaml`:

1. Any required facet `blocked` → **KILL** (redesign or scope-cut may still be possible — see
   the UC's note).
2. Any structural gap → **DEFER**: a dimension ≥2 levels short, a dimension at 0–1 where ≥3 is
   required, or a required facet at 0. These need a prerequisite project, not a task.
3. Any remaining gap (dimension 1 level short, facet partial) → **CONDITIONAL**: approvable
   with a remediation plan ≤90 days (`07-feasibility-gating.md` remediation playbook).
4. No gaps → **GO** (pilot at A1 per the lifecycle; autonomy is earned, not launched).

**A0/A1 start** column: marks CONDITIONAL/DEFER use cases with no data gap and nothing blocked
— these can usually launch immediately as insight-only worklists (one level less on
integration/governance/workflow) while remediation proceeds.

**Highest-leverage remediations**: blocking items ranked by how many use cases they hold back,
with sole-blocker counts. In most assessments a handful of items (governance stack, denial
labels, contract engine load, orchestration fabric) dominate — that ranking is your Wave-0
business case.

## Interpreting a typical result

Don't read `GO: 0` as failure. A mid-maturity organization scores exactly like the example:
most of the catalog CONDITIONAL/DEFER on the same few shared gaps. The correct reading is
sequencing, not verdict — fund the top remediations, launch the A0/A1-available use cases now,
and re-score quarterly. The delta between assessments is your automation-readiness velocity.

## Keeping it honest

- Re-score on a fixed cadence (quarterly) and after any major system/vendor change.
- The assessment file is the record: commit it, diff it, don't overwrite history.
- If a UC scored GO but failed in implementation, the assessment lied — correct the facet
  score and record what evidence would have caught it.
